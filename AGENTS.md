# Правила разработки (AGENTS.md)

## 0. Общее
- Всегда отвечать на русском языке. Комментарии в коде, коммиты, имена — только на английском.
- Проект: бесплатный фанатский компаньон для Arknights (планировщик, склад, фарм, вики, рекрутинг, гача). Бюджет нулевой: собственного сервера нет.
- Минимальный дифф: решение полное, но без лишних правок. DRY, KISS, YAGNI. Ничего «на будущее».
- Перед задачей коротко сообщить план (3–6 пунктов), после — что изменено и как проверено.
- Любое предупреждение линтера/компилятора устранять. Задача не закончена, пока не проходят `lint`, `typecheck`, `test`, `build`.

## 1. Стек
Nuxt 4, Vue 3 (`<script setup lang="ts">`, Composition API, без Options API), TypeScript strict, Pinia (`@pinia/nuxt`), `@vueuse/core`, SCSS, `@nuxtjs/i18n`, `@nuxtjs/supabase`, `@nuxt/icon`, `@nuxt/image`, `@vite-pwa/nuxt`, `@nuxtjs/sitemap`, `nuxt-schema-org`, Zod, Vitest + `@nuxt/test-utils`, Playwright, ESLint + Prettier + Stylelint, Husky + lint-staged. Деплой: Vercel. CI: GitHub Actions.
**Nuxt UI не используется.** Новые зависимости добавлять только по необходимости и с объяснением.

## 2. Структура (Nuxt 4)
```
app/            pages/, components/, composables/, stores/, utils/, assets/styles/, layouts/, plugins/
server/         api/ (Nitro, только прокси и скрытые ключи), utils/
shared/         типы и чистые функции, общие для app и server
data/           сгенерированные JSON (game data, banners, penguin benchmark)
scripts/        скрипты сборки данных и синхронизации (запускаются Node/Actions)
tests/          unit/, e2e/
docs/           архитектурные решения, описания модулей (Markdown)
```
- Использовать автоимпорт Nuxt для компонентов и composables.
- Один компонент — одна ответственность. Повторяющуюся логику выносить в composables.
- Глобальное состояние — Pinia. Локальное — `ref`/`computed`.

## 3. Архитектура и данные
- **Расчётное ядро** (прокачка, декомпозиция крафта, дефицит, рекрутинг, гача, ран-счётчик) — чистые TS-функции в `shared/` без Vue/Pinia/сети. Каждая покрыта unit-тестами. Компоненты только вызывают ядро.
- **Внешние данные** (game data, Penguin Stats, wiki, Yostar) всегда проходят валидацию Zod. Типы выводить из схем (`z.infer`).
- **Данные игры** не парсятся в рантайме браузера: скрипты в `scripts/` генерируют типизированные JSON в `data/`. Обновления данных в CI оформлять через PR с отчётом о различиях, не прямым коммитом в `main`.
- **Ассеты** (аватары, арты, иконки) получать только через единую функцию `resolveAsset()` с цепочкой fallback. Хотлинк на чужие сайты вне этой функции запрещён. Формат WebP, размеры указаны, ленивая загрузка.
- **Рендеринг:** публичные wiki-страницы — prerender/SSR (SEO). Планировщик, склад, фарм, гача — `<ClientOnly>`/клиентские, должны работать offline (PWA).
- **Запросы:** `useFetch`/`useAsyncData` для SSR-данных; для остальных — SWR-подход и кэш. Подгружать компоненты и маршруты лениво.
- **Server (Nitro):** только прокси для обхода CORS и логика с секретами. Секреты — в `runtimeConfig` + `.env`, читать через `useRuntimeConfig()`.

## 4. Безопасность
- Никогда не коммитить API-ключи, секреты, токены. Только `.env` (в `.gitignore`), шаблон — `.env.example`. В коде ключи напрямую не использовать.
- Supabase: на клиенте только anon key. `service_role` в проекте не использовать. Для всех таблиц включена RLS, политики «пользователь видит только свои строки». Миграции хранить в `supabase/migrations/`.
- **Yostar-синк:** логин, код и токены не логируются и не сохраняются на сервере. Прокси stateless. **Исключение по решению владельца (2026-10-21):** токен Yostar-аккаунта хранится на устройстве в `localStorage` под namespaced-ключом `arkcalc_yostar_session` с TTL, чтобы повторный sync не требовал email/код; в Supabase и на сервер он не попадает, при 401/истечении очищается, кнопка Disconnect очищает его вручную. В UI — явное предупреждение, что токен хранится на этом устройстве. Модуль под feature-флагом.
- Не логировать персональные данные.

## 5. Стили (SCSS + БЭМ, без Nuxt UI)
- Только классы. Никаких селекторов тегов и `#id` для стилизации (кроме глобального reset).
- Именование: `block`, `block__element`, `block--modifier` (`block__element--modifier`). Не более одного БЭМ-класса на элемент, кроме микса.
- В SFC: `<style lang="scss" scoped>`. Блок объявляется один раз, элементы — через `&__element` на одном уровне. Вложенность элементов (`&__a { &__b }`) запрещена, глубина не более 2–3 уровней.
- Один компонент — один блок. Общие стили — в `app/assets/styles/` (`_tokens.scss`, `_mixins.scss`, `_reset.scss`, `main.scss`).
- Цвета, шрифты, отступы, радиусы, тени, z-index — только через дизайн-токены (CSS custom properties + SCSS-переменные). Хардкод значений запрещён.
- Дизайн в стиле Arknights: тёмная палитра, угловатые формы (срезанные углы), тонкие линии и сетки, акцентные цвета, моноширинные/технические шрифты для цифр. Адаптивность: mobile-first.
- Иконки через `@nuxt/icon`.

## 6. Локализация
- `@nuxtjs/i18n`, единственный поддерживаемый язык — `en` (английский).
- Никаких строк в шаблонах «вшито»: всё через ключи `t('...')`. Файл переводов — `i18n/locales/en.json` (проверять скриптом `npm run i18n:check`).
- Игровые названия (операторы, предметы, скиллы) берутся из данных официального глоссария (YoStar EN). Неофициальные переводы или заглушки `[Pending Translation]` CN-контента помечаются тактическим бейджем.

## 7. TypeScript и качество
- `strict: true`, `noUncheckedIndexedAccess: true`. Запрет `any` (использовать `unknown` + Zod/типгарды). Явные типы публичных функций.
- ESLint (flat config, строгие правила) + Prettier + Stylelint (SCSS, проверка БЭМ-паттерна класса).
- Husky + lint-staged: перед коммитом линт/форматирование изменённых файлов; `typecheck` и тесты — в CI.
- TDD по возможности: сначала тест (или план), затем код. Новая логика ядра без теста не принимается.
- Скрипты: `dev`, `build`, `lint`, `lint:fix`, `typecheck`, `test`, `test:e2e`.

## 8. Git
- Ветка на каждую задачу (`feat/…`, `fix/…`, `chore/…`), в `main` напрямую не пушить.
- Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `test:`, `refactor:`). Мелкие осмысленные коммиты.
- Перед коммитом смотреть `git diff` и убедиться, что нет секретов и лишних файлов.

## 9. Комментарии и документация
- Комментарии только на английском и только для неочевидной логики. Код самодокументируемый (понятные имена).
- Архитектурные решения и модули документировать в `docs/*.md`. Прогресс и контекст по задачам вести в `docs/progress.md` (что сделано, что дальше, известные проблемы) — чтобы не терять контекст между сессиями.

## 10. Инструменты (MCP)
Использовать при необходимости: Filesystem/Git, Terminal (npm-скрипты, `tsc`, линтеры), Context7 (актуальная документация библиотек), Playwright (проверка UI), Chrome DevTools, Supabase MCP (только dev-проект), Fetch (проверка внешних API), Basic Memory (контекст проекта). Перед использованием новых API/библиотек сверяться с актуальной документацией через Context7.

## 11. Авторские права
Арты, иконки и данные принадлежат Hypergryph/Yostar. Проект некоммерческий и неофициальный; в футере обязателен дисклеймер. Не коммитить в репозиторий игровые ассеты крупными пачками без решения владельца проекта.

## 12. Dev-серверы
- Порт 3000 занят dev-сервером владельца проекта, он смотрит на него в реальном времени. НИКОГДА не запускать, не останавливать, не перезапускай и не освобождай порт 3000 (никаких kill, никаких npm run dev без явного порта).
- Все проверки агента выполняются на http://localhost:3001: `nuxt dev --port 3001` (в Playwright локально тоже 3001). Если 3001 уже слушает собственный процесс агента, переиспользовать его, не плодя новые.
- Два dev-сервера в одной папке делят каталог `.nuxt` и мешают друг другу. Для dev-сервера агента используется отдельный `buildDir`: в `nuxt.config.ts` `buildDir: process.env.NUXT_BUILD_DIR ?? '.nuxt'`, запуск через `NUXT_BUILD_DIR=.nuxt-agent nuxt dev --port 3001` (скрипт `npm run dev:agent`). Каталог `.nuxt-agent` добавлен в `.gitignore`, `.prettierignore` и исключения линтера.
- В `playwright.config.ts`: локально webServer = dev:agent на 3001 (`reuseExistingServer: true`, `baseURL: 'http://localhost:3001'`); в CI остаётся `build + preview`. Порт 3000 локально в конфигах не использовать.

## 13. Единообразие интерфейса
- Страницы строятся только из `app/components/ui/` (`Ak*`) и общего шаблона.
- Если нужен новый паттерн — сначала компонент в `app/components/ui/` и добавление в витрину компонентов `app/pages/_ui.vue`.
- Одноразовые кастомные стили на страницах запрещены, кроме раскладки сетки/отступов страницы.
- Цвета секций строго фиксированы по назначению: янтарь — гача/предупреждения, зелёный — планы/активно, циан — информация/статус.
- Каждая страница обязана иметь состояния загрузки (loading), пусто (empty), ошибка (error) и поддерживать адаптивную раскладку с 360px.
- Каждая страница обязана проходить layout-sanity тесты (без горизонтального скролла на всех брейкпоинтах).
- Любой новый модуль обязательно регистрируется в реестре `app/config/modules.ts`.

## 14. Merge-политика
Агент сам мержит свой PR в main (squash, удалить ветку), если выполнены ВСЕ условия:
1. CI полностью зелёный, Vercel preview READY.
2. Выполнены все критерии приёмки задачи, нет известных багов, влияющих на корректность данных, расчётов или безопасность.
3. Не затронуты зоны ручного одобрения (см. ниже).
4. В отчёте нет непроверенных утверждений: всё, что заявлено как «сверено с источником», подтверждено запросом с URL и датой.

Агент НЕ мержит и ждёт решения владельца, если:
- есть непроверенные эталоны, расчётные формулы с неподтверждёнными допущениями, расхождения с игровыми данными;
- затронуты секреты, токены, ключи окружения и .env.example;
- изменены боевые миграции Supabase и RLS-политики;
- изменена интеграция с Yostar-логином;
- тесты были ослаблены, удалены или помечены skip ради зелёного CI;
- размер data/ или бандла вырос более чем на 25% без согласования.
(Изменения .github/**, CI/CD, зависимостей, лицензий, дисклеймеров и обычного auth-кода разрешено мержить агенту самостоятельно при соблюдении остальных условий).

Мелкие недочёты (косметика, неполные тесты на редкие случаи, улучшения) не блокируют merge: агент записывает их в docs/known-issues.md (дата, задача, описание, приоритет) и в отчёт отдельным списком «Отложено». В начале каждой следующей задачи агент читает known-issues.md и закрывает пункты, которые касаются затрагиваемого кода.

После merge агент: переключается на main, делает git pull, подтверждает, что main зелёный, затем начинает следующую задачу от свежего main.
