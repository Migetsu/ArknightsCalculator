# Architecture Overview

## 1. Technology Stack

- **Framework:** Nuxt 4 (Vue 3, Composition API, `<script setup lang="ts">`)
- **Language:** TypeScript (`strict: true`, `noUncheckedIndexedAccess: true`)
- **State Management:** Pinia (`@pinia/nuxt`)
- **Composables:** `@vueuse/core` (`@vueuse/nuxt`)
- **Styling:** SCSS + BEM methodology (no UI component libraries)
- **Icons & Images:** `@nuxt/icon`, `@nuxt/image`
- **Backend / Database:** Supabase (Client: `@nuxtjs/supabase`, RLS-enabled, stateless proxy for secure integrations)
- **Localization:** `@nuxtjs/i18n` (English, no prefixes)
- **Testing:** Vitest (`@nuxt/test-utils`), Playwright (Chromium)
- **Deployment:** Vercel (CI via GitHub Actions)

## 2. Directory Structure (Nuxt 4)

```text
app/            pages/, components/, composables/, stores/, utils/, assets/styles/, layouts/, plugins/
server/         api/ (Nitro proxies and secret handling), utils/
shared/         types and pure functions shared between app and server
data/           generated JSON (game data, banners, penguin benchmark)
scripts/        data sync and build scripts (Node.js/Actions)
tests/          unit/, e2e/
docs/           architectural decisions, module guides, progress tracking
```

## 3. Core Principles

- **Calculation Core:** Pure TypeScript functions in `shared/` without Vue/Pinia/network dependencies, covered by unit tests.
- **External Data:** Validated via Zod schemas; runtime game data pre-generated by offline scripts in `data/`.
- **Offline / PWA:** Planner, depot, farming, and gacha tools designed for offline client-side functionality.
- **Zero Server Cost:** Serverless Nitro functions only for CORS proxies and secret handling.

## 4. Operator Data Loading Architecture

Operator details and dossiers are generated JSON (`data/operators/*.json`, `data/handbook/*.json`),
but they are **not** imported as JS modules. A dynamic import per file made Vite/Nitro emit one
chunk per operator (1005 server chunks, ~920 client chunks) and pushed builds to OOM.

Current strategy (details and measurements in `docs/server-data-assets.md`):

1. **Build-time aggregation:** `modules/server-data-assets/` groups the files into 8 operator and
   4 handbook bucket files under `.cache/server-data-assets` and exposes them as Nitro
   `serverAssets` (`assets:operators`, `assets:handbook`). `data/` and `data:validate` are
   untouched.
2. **Nitro API endpoints:** `/api/operators/[id]` and `/api/handbook/[id]` validate the id,
   read the matching bucket (in-process cache, bounded by bucket count) and return 404 for
   unknown or malformed entries.
3. **SSR and client:** `useOperatorDetail` / `useOperatorHandbook` keep `useAsyncData` keys,
   `default: null` and `watch` semantics. SSR fetches through `useRequestFetch()` (internal
   request, no absolute origin); client navigations use `$fetch`. The handbook Map cache is
   preserved.
4. **SEO / PWA:** operator pages stay SSR, so dossier text is present in the HTML. The API is
   HTTP-cacheable (`cache-control: public, max-age=3600`) and can be cached by a service worker
   if PWA caching is added later. No operator data is emitted to the client bundle.

Result: server chunks drop to 153, client JS chunks to 51, and the client bundle shrinks by
~23 MB while SSR content and 404 behaviour are unchanged.

## 5. Testing

### Structure

- `tests/unit/`: Unit tests for pure business logic, calculations, and components.
  - Tests for `shared/` run in lightweight `node` environment without Nuxt overhead.
  - Component tests run in `nuxt` environment with `happy-dom` via `@nuxt/test-utils`.
- `tests/e2e/`: End-to-end tests using Playwright (Chromium).
  - `smoke.spec.ts`: Basic page health checks.
  - `i18n.spec.ts`: English-only navigation and i18n integrity.
  - `responsive.spec.ts`: Desktop, tablet, mobile viewports, drawers, modals.
  - `layout-sanity.spec.ts`: Viewport-wide overflow defense (`scrollWidth <= clientWidth`), missing key detection, and component collision validation.
  - `fixtures.ts`: Page error and `console.error` assertions, preventing regressions.

### Running Tests

- `npm test`: Run all unit tests with Vitest (`vitest run`).
- `npm run test:watch`: Run unit tests in watch mode (`vitest`).
- `npm run test:e2e`: Run Playwright e2e tests (`playwright test`).

### Guidelines

- All calculation core modules in `shared/` must be thoroughly covered by unit tests.
- E2E tests focus on critical user flows (smoke tests, navigation, core workflows) and layout sanity without horizontal overflow.

## 6. Development Server Isolation

- **Owner Dev Server:** Port 3000 is reserved for live development by the project owner. Automated agents must never start, stop, or reload port 3000.
- **Agent Dev Server:** Runs on `http://localhost:3001` via `npm run dev:agent` (`scripts/dev-agent.mjs`) with isolated `.nuxt-agent` build directory (`NUXT_BUILD_DIR=.nuxt-agent`).
- Playwright tests locally target `http://localhost:3001` and reuse the agent server process (`reuseExistingServer: true`).

## 7. Storage Architecture & Versioned Migrations

- **StorageAdapter Layer:** Abstract async key-value interface (`app/utils/storage/`) implemented via native `IndexedDbAdapter` (zero bundle overhead) with isomorphic SSR fallback to `MemoryStorageAdapter`.
- **Schema Versioning:** State payloads (Depot, Planner) define explicit `CURRENT_SCHEMA_VERSION`.
- **Legacy v0 Compatibility:** The `v0` fallback migration branch in `app/schemas/depot.ts` supports unversioned prototyping structures (flat item dictionaries) from early development experiments before formal versioning. While production storage writes strictly versioned schemas (`schemaVersion: 1`), this migration routine is preserved to ensure seamless upgrades for early developer local environments.
- **Corruption Resilience:** If data cannot be validated or migrated, an emergency backup is saved (`arkcalc_depot_corrupted_<timestamp>`), alerting the user and safely re-initializing clean storage without crashes.
