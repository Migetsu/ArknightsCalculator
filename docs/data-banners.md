# Banners Dataset (`data/banners.json`)

## 1. Overview & Architecture

`data/banners.json` provides a fully typed, machine-readable dataset of Arknights headhunting banners across both Global (EN) and Chinese (CN) servers. It is generated by `scripts/data/build-banners.ts` (`npm run data:banners`) directly from official game client data tables (`.cache/raw/{cn,en}/gacha_table.json`).

The dataset serves as the foundation for the gacha calculator, banner timelines, active banner countdowns, and future banner forecasting.

```
.cache/raw/{cn,en}/gacha_table.json (gachaPoolClient)
                      │
                      ▼
          scripts/data/build-banners.ts
       (Filtering + LMTGSID Matching + Meta)
                      │
                      ▼
              data/banners.json
       (Validated by shared/schemas/banner.ts)
```

---

## 2. Dataset Structure

The root JSON object is structured according to `BannersDatasetSchema` in `shared/schemas/banner.ts`:

```typescript
export interface BannersDataset {
  meta: BannersMeta
  cnBanners: GachaBanner[]
  enBanners: GachaBanner[]
  banners: GachaBanner[]
}
```

### 2.1 Meta (`meta`)

Metadata generated at build time:

- `generatedAt`: ISO 8601 generation timestamp.
- `currentEnBanner`: The primary active EN banner (prefers active LIMITED banner, or latest active standard banner).
- `activeEnBanners`: List of all banners currently open on EN.
- `activeCnBanners`: List of all banners currently open on CN.
- `nextEnLimitedBanner`: The next upcoming limited banner for EN, identified through CN progression.
- `nextEnBanner`: Currently populated for limited banners.

### 2.2 Banner Entry (`GachaBanner`)

Each banner object contains:

- `id`: Unique game pool identifier (e.g. `LIMITED_EN_42_0_1`, `NORM_0_1_1`).
- `server`: `'en' | 'cn'`.
- `ruleType`: Raw game rule type (e.g. `'LIMITED'`, `'LINKAGE'`, `'NORMAL'`, `'SINGLE'`, `'DOUBLE'`).
- `type`: High-level category: `'limited' | 'standard' | 'joint_operation'`.
- `name` / `title`: `I18nString` (`{ en: string, zh: string, source: I18nSource, isMachineTranslation: boolean }`). Localized pool title, resolved through the layered i18n pipeline (`resolveLayeredI18nString` with key `banner.${id}.name`). For CN-only banners, English translations are provided by machine translation (`data/i18n/machine/banners.json`) with an `MT` badge, or `[Pending Translation]` with a `PENDING` badge if uncollected.
- `openTime` / `endTime`: Exact Unix timestamps in seconds.
- `openIso` / `endIso`: Standard ISO 8601 strings (e.g. `2026-10-14T10:00:00.000Z`).
- `durationDays`: Duration of the banner in fractional days.
- `isActive`: Boolean flag indicating if banner is active at generation time.
- `lmtgsid`: Limited headhunting coin/currency identifier (e.g. `LMTGS_COIN_7301`), or `null`.
- `pairedBannerId`: ID of the paired banner on the counterpart server (populated for limited banners via `LMTGSID`), or `null`.
- `isNextEnBanner`: Boolean flag marking the next upcoming limited banner in `cnBanners`.
- `rateUp6` / `rateUp5`: Array of operator IDs (see Section 5 below).

## 3. Data Cleaning & Filtering

Raw tables contain 409 EN pools and 454 CN pools. To keep the dataset relevant and clean, two categories of pools are excluded:

### 3.1 Starter Pools

- **Criteria**: Pool ID begins with `boot_` or contains `newbee`.
- **Finding**: In official data, starter pools are stored in a separate table property `newbeeGachaPoolClient` (`BOOT_0_1_1..3`), leaving 0 starter pools in `gachaPoolClient`.

### 3.2 Perpetual / Returning Pools

- **Criteria**: Rule type is `BACKFLOW`, duration exceeds 180 days (`durationDays > 180`), or scheduled end time extends past the year 2030.
- **Excluded**:
  - EN: `RETURN_EN_41_0_1` ("Return Headhunting", duration 1,523 days, ends `2030-10-14`).
  - CN: `RETURN_71_0_1` ("回归寻访", duration 1,513 days, ends `2030-04-30`).
- **Retained Count**:
  - EN: 408 pools retained (out of 409).
  - CN: 453 pools retained (out of 454).
  - Combined `banners`: 861 banners.

### 4.3 Positional Method Benchmark & Non-Limited Pool Divergence

We evaluated whether sorting EN and CN pools chronologically and pairing by position index is valid:

1. **LIMITED pools**: Positional alignment yields 25 matches out of 25 (100% precision).
2. **Non-limited pools (SINGLE, DOUBLE, NORMAL)**: Positional alignment **fails** due to schedule divergences between Yostar and Hypergryph:
   - In `SINGLE` pools, events 8 and 9 were swapped by Yostar ("Ray of Light" vs "To Bloom From a Dim Flame").
   - In `DOUBLE` pools, EN has 31 while CN has 43 (divergence of 12).
   - In `NORMAL` standard rotation pools, EN has 223 while CN has 233 (divergence of 10).
3. **Decision**: In strict accordance with AGENTS.md §0 (zero unverified guesswork), `pairedBannerId` is only populated when verifiable via `LMTGSID`. For non-limited banners, `pairedBannerId` is left as `null`.

## 5. Rate-Up Operators Sourcing Decision

In legacy game tables (2019–2020), banner details contained HTML markup listing rate-up operators. In modern game client data, `gachaPoolDetail` is intentionally replaced with `"-"` (287 out of 409 EN pools, 302 out of 454 CN pools, including 100% of modern and future pools).

Rather than populating fake data or creating an unmaintained manual list, `rateUp6` and `rateUp5` default to empty arrays `[]`. This preserves backward compatibility with the existing gacha calculator UI without introducing incorrect assumptions.

---

## 6. Validation & Quality Gates

The banners dataset is validated as part of `scripts/data/validate-data.ts` (Step 9):

1. **Schema Check**: Validated against `BannersDatasetSchema`.
2. **ID Uniqueness**: Confirms 0 duplicate banner IDs.
3. **Interval Sanity**: Confirms `openTime < endTime` for every banner.
4. **Absence of Perpetual Pools**: Verifies no banner has duration > 180 days or rule `BACKFLOW`.
5. **Absence of Starter Pools**: Verifies no starter pools remain.
6. **Chronological Sorting**: Verifies `cnBanners` and `enBanners` are strictly ascending by `openTime`.
7. **Meta Integrity**: Confirms referenced banners in `meta` exist within the dataset.

## 7. Display Order, Incremental Rendering & UI Presentation (`app/pages/gacha.vue`)

### 7.1 Display Hierarchy

In accordance with owner product decisions:

1. **Top Highlight (Current Global Banner)**: Rendered at the top of `/gacha` as a prominent hero section using `meta.currentEnBanner` (`LIMITED_EN_42_0_1`, "Sealed With Time"). Shows human-readable formatted end dates (`Oct 28, 2026`), countdown, and links directly to the gacha probability calculator.
2. **CN Archive (Full Timeline)**: Below the current banner, renders the full CN timeline of 453 banners sorted strictly chronologically ascending by start date (`openTime`, earliest at top, latest at bottom).
3. **Active CN Banners**: Any CN banners active at current time (`DOUBLE_77_0_5`, `SINGLE_78_0_1`, `CLASSIC_DOUBLE_78_0_1`) are contained within the timeline and highlighted with an `ACTIVE NOW` tactical badge.

### 7.2 Proven "Not on Global yet" Badge Scope

- Strictly evaluated by `isProvenNotOnGlobal(banner)`.
- **Condition**: Returns `true` if and only if `server === 'cn' && ruleType === 'LIMITED' && !pairedBannerId`.
- **Match Count**: Exactly **1** out of 453 CN banners qualifies: `LIMITED_76_0_1` ("车辙与风的归所", `LMTGS_COIN_7601`).
- **Standard / Rotation Banners**: All 427 non-limited banners have `pairedBannerId === null` due to schedule divergence and never receive a "Not on Global yet" badge, strictly preventing false claims or unverified guesswork (AGENTS.md §0).

### 7.3 Empty Rate-Up Handling (`GachaBannerCard.vue`)

- Modern client tables use `gachaPoolDetail: "-"`, leaving `rateUp6` and `rateUp5` as empty arrays `[]`.
- `GachaBannerCard.vue` calculates `hasContent = rateUp6.length > 0 || rateUp5.length > 0`.
- When `hasContent` is `false`, the rate-up operator section is completely omitted, and `.gacha-banner--no-rateup` is applied to render a clean, compact single-column card.

### 7.4 Performance & Incremental Rendering

- Mounting 453 complex banner cards with image hooks simultaneously causes severe initial render lag.
- Implemented client-side chunking: `PAGE_SIZE = 20`, `visibleCount = ref(20)`.
- Initial mount renders only the first 20 cards.
- Users can progressively load more via "Show More (+20)" or "Show All (453)".
- Changing filters resets `visibleCount` back to 20.

### 7.5 Mobile Responsiveness (360px)

- Cards use flexible box layout with `min-width: 0` and word-break wrapping.
- Zero horizontal overflow across all viewports from 360px to 1920px.
